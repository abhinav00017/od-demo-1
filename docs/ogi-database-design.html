Design draft

One database, many clients.

How our database keeps every client apart, and keeps Ogi inside its own client. High-level design, 15 Nov 2026.

1What is in the database today

All our demos share one Neon database. Today it holds two demo businesses.

The design below is built for many real clients, even though only demos exist today.

2Every client is an organization

One new list, organizations. One row per client. Two clinics on our clinic website are simply two rows.

  • The organization ID never changes. It is what the lock uses. (The IDs above are examples.)
  • The slug is only a name for web addresses. A client can rename it, and none of their rows change.

3Every row carries its organization ID

Every table gets one column, org_id. It says whose row it is.

Example roworg_id

  • The database fills it in by itself. A booking takes it from its clinic, a quote item from its quote, a message from its booking or customer. Code cannot forget it or get it wrong.
  • A new clinic works the same way the moment it is added. No code change.

4How a request finds its organization

Owners and staff belong to one organization, with a role (owner or staff). onlydevs super admins sit above all organizations, with a separate, stronger login. Ogi never gets super admin power.

5Two doors into the database

The app keeps its normal door. Ogi gets its own, much smaller door.

Ogi's door has no password, so nobody can log in with it. The app opens it for one request at a time.

6What happens when Ogi reads data

The lock is inside Postgres itself, so even a bug in our code cannot get around it.

7Extra safety nets

  • Ogi never writes to the database. A booking from Ogi goes through the booking form's own checked code, and only after the visitor presses Confirm.
  • Only known organizations. Ogi's database helper refuses any organization that is not in the organizations list, and any query that is not a plain read.
  • A guard in the migration. If anything about the tables looks unexpected, the migration stops by itself. It can never hide data from the app.

8Why one shared database

This is the industry's standard design for many small businesses: one database, every row labelled with its organization, a lock per organization. It is cheap and simple to run. A big client can move to their own database later without changing the design.
